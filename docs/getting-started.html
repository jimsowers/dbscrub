Getting started

DbScrub

Replace real personal data in a locally restored SQL Server database with obvious fakes — so daily development never touches real people's information.

.NET 10 SQL Server 2019+ localhost only no ORM 360 unit tests

Working end to end

clean masks the database, sweeps every string column for anything that still resembles personal data, and marks the copy as cleaned only if that sweep comes back empty. If it doesn't, you get the list of columns that failed and no mark — so status can never call a database safe on the strength of a run that didn't check.

Renaming the database after a clean run, and reconnecting restored users to local logins, are deliberately not built — nothing uses them, cleaning happens in place, and rename is the most destructive thing this tool could do.

Part 1

Running it

Eight steps from a fresh clone to a masked database. Steps 4 and 6 only ever read — you can run them as often as you like while you get the config right.

  1. 1

    Build it

    You need the .NET 10 runtime and a SQL Server running on your own machine, using Windows authentication. report and status only need to read the database structure; clean also writes to the tables it masks and runs ALTER DATABASE and ALTER TABLE — in practice, db_owner on the copy.

    dotnet build
  2. 2

    Make a practice database

    Optional

    Builds DbScrubTest, a small database full of fake data shaped like the real thing — a temporal table, change tracking, an audit table, and a table with no primary key. It drops and recreates, so it is also how you get back to a known state after a run.

    sqlcmd -S "localhost\MSSQLSERVER02" -E -i scripts\create-test-db.sql
  3. 3

    Write a config

    One JSON file describing what to do with each column. Start with almost nothing — step 4 will tell you what to add.

    {
  "defaults": { "allowedServers": ["localhost"] },
  "tables": []
}
  4. 4

    Ask what would happen

    Read only

    Reads the database, compares it to your config, and prints the plan: which tables get emptied, which columns get masked and how, and everything still unclassified. Changes nothing.

    dbscrub report --server localhost --database MyDb --config my-config.json
  5. 5

    Paste the answer back, then repeat step 4

    The report ends with every column nobody has classified yet, already formatted as JSON. Paste it into your config, change keep to a real strategy wherever the column actually holds personal data, and run report again. Repeat until the unclassified list is empty.

    This loop is the intended way to build a config. Nobody can list every column in a production database from memory.

  6. 6

    Dry run

    Read only

    The same plan, but reached through clean's own safety checks — so it also proves the server allowlist and the config would let a real run start. Never prompts, so it is safe inside a script.

    dbscrub clean --server localhost --database MyDb --config my-config.json --dry-run
  7. 7

    Clean it

    Modifies data

    Prints the plan, then asks you to type the database name exactly before it changes anything. Add --yes to skip the prompt — allowed only on localhost, . or 127.0.0.1, with or without an instance name.

    dbscrub clean --server localhost --database MyDb --config my-config.json

    Add --fail-on-unclassified to refuse to run while any column still has no verdict, whatever the config says. There is deliberately no flag that loosens it.

  8. 8

    Check it

    Read only

    clean already ran the verification sweep and wrote the mark, so this is the independent second opinion — the one a script or a build step can ask without doing anything.

    Answers “has this database been cleaned?” so scripts and build steps can branch on the exit code. --config is optional here and is read only for the list of allowed servers — you need it if your SQL Server is a named instance.

    dbscrub status --server localhost --database MyDb

Running it without installing anything

Every dbscrub above can be run straight from the repo as dotnet run --project src/DbScrub.Cli -- report --server …, or from the build output at src\DbScrub.Cli\bin\Debug\net10.0\dbscrub.exe.

Exit codes

These are a contract — CI depends on them, so they are never renumbered, only added to.

CodeMeaning
0Success. For status, the database is clean. For clean, also returned when the database was already clean and was skipped
1Something unexpected went wrong — including a run that failed partway, or one that could not rewrite every row
2Verification found values that still look like personal data, so nothing was marked — or, for status, the database is not clean
3Unclassified columns while set to fail, or clean --fail-on-unclassified
4A safety check refused: server not on the allowed list, wrong database name typed, or --yes used on a server that is not unambiguously local
5The config is invalid, or it asks for something the schema cannot do — a static value that will not fit, a scramble on a table with no primary key, a column that no longer exists

Five things that stop a run

DbScrub is designed on the assumption that someone will eventually point it at the wrong database. The first four refuse before anything is modified; the last one refuses to call the result clean.

The server is not on your allowlist

Every command checks allowedServers before opening a connection. There is no override flag and no environment variable — if you need another server you edit the config, and that edit shows up in a diff. Matching is exact: localhost does not cover localhost\SQL2022.

The database was already cleaned

Skipped rather than cleaned twice, and it exits 0 — so a wrapper script that re-runs it carries on instead of failing.

You typed the wrong name

The allowlist catches the wrong machine. Typing the database name catches the wrong database on a machine that is legitimately allowed. Pressing a key is muscle memory; reproducing a name from the summary is not.

Rows were left unmasked

Each table's row count is taken before the rewrite and compared afterwards. If they disagree, rows kept their real values — so the run reports failure, because a skipped row is otherwise completely silent.

Verification found something

After masking, every string column is swept for anything that still looks like personal data. A hit means the database is not marked as clean, and you get the list of columns — never the values. See the gate.

Why it is split this way

Stages 1–5 never touch the database, so the entire plan is a pure function of (schema, config). That is what lets report show you the real statements rather than a paraphrase, and what lets every one of them be asserted in a unit test. A problem found at plan time stops a run; the same problem found mid-run leaves a database that is neither raw nor clean.

What a clean run actually does

Three phases. The first and third are the same operation, deliberately pulled apart so that masking happens in between.

Phase 1 — before

Hygiene

HygienePlanner.BuildPreMask
  • Set the database to SIMPLE recovery
  • Disable change data capture
  • Turn OFF system versioning
  • Empty temporal history tables, unless the config asks for them to be masked instead
  • Empty tables marked truncate
Phase 2

Masking

CleanRunner → SqlCleanSession
  • Rewrite every configured column
  • In batches, one transaction each
  • Row counts reconciled per table
Phase 3 — after

Hygiene

HygienePlanner.BuildPostMask
  • Turn system versioning back ON
  • Runs even if masking failed or was cancelled — a table left detached silently records no history, and nothing about the database looks wrong

Why phases 1 and 3 are not adjacent

While system versioning is ON, every UPDATE copies the row's old value into a hidden history table. Masking with versioning on would not clean the database — it would move the real data somewhere less obvious and then report success. So versioning is turned off in phase 1 and only restored in phase 3. There is deliberately no method that returns both phases in one list.

Then the gate: check, and only then claim

Masking finishes, and DbScrub does not take its own word for it. Two more steps run, in this order and only in this order.

1 — Verify

Sweeps every string column in the database, not only the ones you configured — the columns nobody classified are exactly where something is most likely to have been missed. Looks for email addresses, Social Security numbers, and three punctuated phone shapes.

Any hit and the run stops here: the columns and match counts are printed, nothing is marked, and the exit code is 2.

SqlVerifierVerifyPattern

2 — Stamp

Only reachable from a verify that found nothing. Writes four database properties — cleaned yes/no, when, which config, which tool version — plus a row in dbo.__SanitizationLog as the audit trail.

This is what dbscrub status reads, and what a consuming application will eventually read to refuse to start against an uncleaned copy.

StampWriterStampRecord

Why the order is the whole point

A raw copy and a scrubbed copy have the same name — DbScrub cleans in place, so nothing about the database tells you which one you are looking at. The mark is the only difference. Written without the check that earns it, it would make status confidently wrong, and every script and person trusting status wrong with it.

So one class owns both steps rather than leaving the sequence to whoever calls them, and a verify that crashes counts as a verify that did not pass. If the mark fails to write on an otherwise clean database, that is the safe direction: you get a clean database that says it is dirty, and the cost is a re-run.

The catch that makes this harder than it sounds

scramble preserves shape on purpose, so a scrambled SSN is 999-99-9999 — which matches the SSN pattern perfectly. Taken at face value, a correctly scrubbed database could never pass verification and could never be marked clean.

So the sweep also knows what this tool's own output looks like, and excuses it. That rule is deliberately conservative: a value has to be entirely placeholder characters, so a real value that merely contains a 9 is never waved through.

Three ways a table gets rewritten

Chosen per table by MaskPlanner, never by the executor. The deciding question is whether any new value depends on the row's current value.

Row by row

Used when any column is scramble. Walks the table in primary key order in batches, computes each new value in memory, and writes the batch back addressing each row by its key.

MaskMode.RowByRow

Batched constant

Every new value is the same and the table has a primary key. One set-based UPDATE per key range, and no rows are read at all — the walk exists only to keep each transaction small.

MaskMode.BatchedConstant

Whole table

Every new value is the same, and there is no primary key. One UPDATE, one transaction. Correct but unbounded, so the report names these tables separately.

MaskMode.WholeTable

Two things DbScrub will refuse

Masking a primary key column. The engine walks a table in key order, so changing the key underneath that walk skips rows — and a skipped row keeps its real values. Masked keys also collide with each other and orphan every row referencing them. Use keep.

Scrambling a table with no primary key. Scrambling writes a different value to every row, which means being able to point at one row, which needs a key. Add a key, or use static / null — those write the same value everywhere and need no key.

The four column strategies

StrategyWhat happensNotes
static Every row gets the fixed value you supply Type- and length-checked against the real column before the run starts
scramble Letters become x, digits become 9, punctuation is kept Length and shape survive, so forms still validate. Needs a primary key
null Emptied Only valid if the column allows nulls — checked against the live schema
keep Left alone. You looked, and there is no personal data here Records that a decision was made, so it leaves the unclassified list

scramble keeps a value's shape — sometimes that is the wrong thing

A scrambled Social Security number is 999-99-9999: still unmistakably SSN-shaped, and still telling a reader that this column holds Social Security numbers. That is deliberate — preserving shape is what keeps the copy usable, because forms still validate and column widths still hold. But where the shape itself is the sensitive part, use static instead. The sample config masks Email with static for exactly this reason.

Whole tables, in one line

"strategy": "truncate" deletes every row — for audit trails, email logs and message queues, where old values hide inside JSON that no column rule could reach into. "strategy": "keep" declares a whole table clean and requires a reason, so an exclusion is a recorded decision rather than a way to make the report quiet.

DbScrub never prints a real value. Not in the report, not in errors, not in tests.
